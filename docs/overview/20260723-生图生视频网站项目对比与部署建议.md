# 生图生视频网站项目对比与部署建议

## 结论

若目标是上线一个可收费、可持续维护的生图和生视频网站，建议以已有的 OpenLovart 为主项目继续开发，参考本项目的异步任务、素材存储和管理后台设计。不要把两个项目直接合并。

## 项目对比

| 维度 | infinite-canvas | OpenLovart |
| --- | --- | --- |
| 图片生成 | 已覆盖多模型、历史、素材和工作流 | 已有稳定的生成入口，以及使用码、积分预扣和失败退款 |
| 视频生成 | 已有异步任务、状态轮询、生成历史，以及图像、视频、音频参考素材 | 已有画布面板和接口，但任务状态及结果保存仍需加强 |
| 用户与运营 | 有登录、管理员、用户积分、模型和存储配置后台 | 使用码免登录模式更适合轻量商业产品，但运营后台较少 |
| 数据与素材 | 支持数据库、SQLite、本地及 S3/R2 对象存储 | 积分已使用 Supabase；项目和异步资源仍有本地文件依赖 |
| 部署 | Docker 部署路径已具备，但仍在开发中 | 页面可部署到 Vercel，但不能直接承担长期视频任务和本地文件存储 |
| 商业授权 | AGPL-3.0，在线服务的修改分发会带来源码公开义务 | 上游声明 MIT，商业化更灵活，发布前仍应核实许可证 |

## 关键判断

- OpenLovart 已有的使用码、积分、预扣和退款，是商业化最值得保留的基础。
- 视频生成是异步长任务，不能依靠用户浏览器持续打开或本地磁盘保存结果。
- 本项目适合作为任务管理、模型渠道、素材管理和后台运营的架构参考。
- 若希望保持商业项目闭源，不应直接将 AGPL 项目作为产品代码底座或复制其实现。

## 推荐架构

```text
用户画布 / 生图 / 生视频
          │
          ▼
Next.js（现有 OpenLovart 界面、使用码、积分）
          │
          ├── 图片：同步提交并返回结果
          │
          └── 视频：创建任务 → 保存状态 → 后台查询 → 返回结果
                                      │
                         ┌────────────┴────────────┐
                         ▼                         ▼
                   Supabase Postgres              R2 对象存储
               任务、积分、流水、项目          图片、视频、参考素材
```

## 推荐实施顺序

1. 将 OpenLovart 的项目文件、图片和视频结果迁移到 R2 或 Supabase Storage，并把画布项目数据保存到数据库。
2. 建立统一生成任务中心，记录图片和视频任务的模型、成本、状态、结果地址和失败原因。
3. 视频任务改为后台持续轮询；用户关闭页面、服务重启或请求超时后仍可恢复任务结果。
4. 把视频生成接入现有积分服务，采用预扣、成功结算、失败退款的同一规则。
5. 增加最小运营后台：使用码、余额、任务、失败补偿、模型开关和价格配置。
6. 在底层闭环稳定后，再补工作流、提示词库和素材管理等体验功能。

## 当前优先级

最应优先完成的是“异步视频任务、持久化存储、视频扣费”闭环。完成后，OpenLovart 才具备稳定部署和收费运营的基础。
